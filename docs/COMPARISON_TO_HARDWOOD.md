# Hardwood vs. ZPQ: A Comparative Analysis & Adoption Roadmap

## Executive Summary

**Hardwood** is a "minimal dependency" Java implementation of Parquet that prioritizes correctness and breadth of format support (encodings, codecs) over raw specialized speed (initially). It has an excellent, disciplined roadmap and comprehensive coverage of the Parquet spec despite being "alpha".

**ZPQ** is a "grumpy elitist" Zig implementation that prioritizes raw throughput, zero-copy architecture, and predictable memory usage. It currently lacks the breadth of format support that Hardwood has but beats it on foundational architecture (native code vs JVM).

**Strategic Value**: We should view Hardwood as a "feature completeness map" for ZPQ. We can adopt its disciplined "Phase" approach to roadmap our own feature expansion, specifically prioritizing the encodings and codecs we are missing to handle real-world data lakes.

## Feature Matrix

| Feature | Hardwood (Java) | ZPQ (Zig) | Winner / Notes |
| :--- | :--- | :--- | :--- |
| **Thrift Parsing** | Manual (No libthrift) | Manual (No libthrift) | **Tie**. Both avoid bloat. |
| **Compression** | Snappy, Zstd, LZ4, GZIP, Brotli | Snappy, Zstd | **Hardwood**. ZPQ needs LZ4/GZIP. |
| **Encodings** | PLAIN, RLE, DICT, DELTA_*, BYTE_STREAM_SPLIT | PLAIN, RLE_DICTIONARY | **Hardwood**. ZPQ matches RLE/DICT but lacks Delta. |
| **Parquet Versions** | V1 and V2 | V1 (Implicitly mostly) | **Hardwood** handles V2 data pages explicitely. |
| **I/O Model** | Blocking I/O (InputStream) | Async / Zero-Copy (io_uring/epoll) | **ZPQ**. Much better for high-throughput S3. |
| **Memory Model** | GC / Object-heavy | Arenas / Manual layout | **ZPQ**. Predictable memory usage. |
| **SIMD** | No (Java Vector API potential?) | Yes (Explicit SIMD loops) | **ZPQ**. |

## Architectural "Theft": What to Adopt

The most valuable thing to steal from Hardwood is its **disciplined roadmap structure** and specific **encoding algorithms**.

### 1. The "Phase" Roadmap
Hardwood breaks down Parquet implementation into very clear, testable phases. ZPQ is currently a mix of "Advanced S3 Sink" and "Basic Reader". We should formalize our Reader roadmap similarly:

*   **Phase 1: Basic Encodings** (Done: PLAIN, RLE, DICT)
*   **Phase 2: Modern Encodings** (Todo: DELTA_BINARY_PACKED, DELTA_BYTE_ARRAY)
*   **Phase 3: Compression** (Todo: LZ4, GZIP)

### 2. Missing Encodings (Priority Order)
Hardwood implements these, and we need them for compatibility with data generated by Spark/PyArrow/DuckDB:

1.  **DELTA_BINARY_PACKED**: Used heavily for integers. ZPQ's `rle.zig` is close but needs the block-level logic.
2.  **DELTA_BYTE_ARRAY**: The default for Strings in many modern writers. Not having this breaks reading many files.
3.  **BYTE_STREAM_SPLIT**: Essential for Float/Double performance.

### 3. Missing Codecs
1.  **GZIP**: Ubiquitous in older usage.
2.  **LZ4**: Very common in modern data lakes (fast decompression).

## Proposed ZPQ Roadmap (Inspired by Hardwood)

We should restructure our work into these actionable milestones:

### Milestone 1: The "Modern" Data Lake Reader
Focus: Read files produced by modern configs of Spark/Arrow.
- [ ] Implement `DELTA_BINARY_PACKED` decoder.
- [ ] Implement `DELTA_BYTE_ARRAY` decoder.
- [ ] Implement `DELTA_LENGTH_BYTE_ARRAY` decoder.
- [ ] Add `LZ4_RAW` and `GZIP` decompression support.

### Milestone 2: The "Writer" Foundation
Hardwood is also planning a writer. We are ahead here with our S3 Streamer, but we need to ensure our encoding quality matches.
- [ ] Verify our `RLE` Encoder (currently used for levels) works for Dictionary Indices.
- [ ] Implement `DictionaryEncoder` (hashing values -> indices).

### Milestone 3: Advanced Types
- [ ] `DECIMAL` support (Logical type on top of Fixed Len Byte Array).
- [ ] `TIMESTAMP` / `DATE` Logical type casting (ZPQ reads them as i64 currently, needs type-aware wrappers).

## Conclusion
Hardwood is a great reference verification implementation. If we implement a new encoding in ZPQ, we can generate a file using Hardwood (once its writer is ready) or verify our reading logic against Hardwood's understanding of the spec.

**Immediate Action**:
1. Check off `DELTA_BINARY_PACKED` as the next specialized decoder to implement in `zpq`.
2. check off `LZ4` as the next compression codec to bind.
