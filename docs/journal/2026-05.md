# Journal — 2026-05

## 2026-05-05

### Streaming, encoders, CLI, and a one-branch repo

Long arc today. The v2-sans-io branch had been carrying B3 (streaming
output) half-done; it ended with B4, E1–E5 all shipped, a CLI v0,
and the whole thing collapsed onto main. Notes by chunk so future-me
can find threads to pull.

#### B3 — streaming output sink

The `MultipartSink` in `src/io/multipart_sink.zig` is the Vortex
"byte-aware permits" idea wearing DuckDB's "bounded concurrency"
clothes. Producer-side `push(bytes)` accumulates into a bounded
buffer; when the buffer crosses TARGET_PART_SIZE (19 MB) it slices a
part and hands it to a worker pool. Backpressure is a byte-count
mutex+condition — producers wait for in-flight bytes to drop, not
for slot count. close() finalizes via either CompleteMultipartUpload
(N≥2 parts) or a single PutObject if only one part materialized.
DELETE was missing from `http.Method` for AbortMultipartUpload —
added that.

The streaming Parquet writer in `src/core/writer/streaming.zig` is
intentionally generic: a `Sink` is `{ ctx, write_fn }`. Encoder loop
calls `sink.write_fn` instead of an `ArrayList.append`. Same writer
used by lambda S3 sink, CLI local file, and tests.

Working set ceiling went from ~2× working RG (decode + encode +
output buffer) to ~1× (decode + encode, output streamed away).
Lambda no longer cares whether the output is 100 MB or 100 GB.

#### B4 — streaming input

Wanted "single decoder, parallel fetchers" — one decoder loop on the
main task, fetcher tasks pre-loading the next RG while the decoder
chews on the current one. The naive form (one Io.Group per file)
regressed bench by 39–81% because cross-file fan-out had been doing
real work. Probe confirmed: a 10-file dataset with 16 RGs each
benefits hugely from N×N concurrency, not N×1.

Pivoted: keep cross-file Io.Group as the outer scaffold, single-
decoder per file as the inner loop. `fileFetchTask` pre-fetches RGs
into a small ring buffer, decoder pops them off. The "FetcherCtx"
struct accumulates fetch_ns timings so per-phase instrumentation
sees overlap directly. fetch_concurrent_ms is reported as a *sum*,
not a max — sum > wall-clock-fetch is the headline number for
overlap value.

Memory ceiling settled at ~150 MB working set across all input/output
sizes after B3+B4. That was the unlock — Lambda's smallest tier is
viable for arbitrary parquet sizes.

#### E1 — snappy compression, with a Zig footgun

Encoder needed compression to hit Spark/PyArrow parity. Wrote
`src/core/parquet/snappy.zig` with both encode and decode. Ran
cross-impl validation against `cramjam.snappy.decompress_raw` —
mismatched. Round-trip with our *own* decoder was clean, which was
the worrying sign: self-consistent but wire-wrong.

Bug was in the copy-tag emit:

```zig
// BUGGY:
dest[d_idx] = @intCast(((copy_len - 1) << 2) | 2);

// FIXED:
const tag_byte: u8 = @intCast((@as(usize, copy_len - 1) << 2) | 2);
```

Zig 0.16 result-location semantics narrowed the shift to u8 *before*
evaluating, dropping the high bit of `(copy_len - 1) << 2` whenever
copy_len > 32. Decoder happily round-tripped its own corrupt output
because the inverse op was equally wrong-shaped.

Lesson: cross-impl validation is the only validation that matters.
Self-consistent codecs lie.

#### Vendored snappy

Native snappy.zig encode benched at ~75 MB/s, well below google
snappy's ~250 MB/s. Vendored google/snappy 1.2.1 (`vendor/snappy/`),
compiled as C++17 via Zig's bundled clang. Patched out the AVX2
fast path (`#if 0` around the `__m256i` block in snappy.cc:1239)
because it referenced `_mm256_*` intrinsics under `defined(__AVX__)`
without including immintrin.h on every code path. Fallback memmove
is fine.

`vendor/snappy/root.zig` exposes a thin Zig FFI:
```zig
pub fn compress(src: []const u8, dest: []u8) Error!usize
pub fn maxCompressedLength(src_len: usize) usize
```

Encode rate: 75 → 250 MB/s. Won 9% on the balanced workload.

#### E2/E3 — zstd + gzip

ZSTD via vendored libzstd C API (allyourcodebase/zstd, fetched by
`build.zig.zon`). Build flags: `decompression=false, dictbuilder=
false` — std.compress.zstd handles decode pure-Zig, no need to
double up. Default level 3 (matches upstream).

GZIP via std.compress.flate.Decompress (decode only — write side
isn't a priority; nobody asks ZPQ to *emit* gzipped parquet).

`compression.zig` is now a clean dispatch: SNAPPY / ZSTD /
UNCOMPRESSED on encode; SNAPPY / ZSTD / GZIP / LZ4_RAW /
UNCOMPRESSED on decode.

#### E4 — dictionary writer + instrumentation

RLE_DICTIONARY for byte-array columns. First cut at 50% cardinality
threshold actually *regressed* encode_ms 316 → 396 — discovered via
the just-shipped per-phase instrumentation. The hashmap inserts on
high-cardinality columns swamped the savings on the rare low-cardin-
ality wins.

Tightened the threshold to 25%. encode_ms 396 → 271, below the pre-
E4 baseline. Dict path triggers only when it'll actually win.

The instrumentation itself is a `Timings` struct in lambda/main.zig
populated through phase callbacks. JSON envelope to stderr (fd=2)
both locally and in Lambda — CloudWatch picks up stderr identically
to stdout, so the same shape works for both.

#### E5 — delta encoders

DELTA_BINARY_PACKED for i32/i64 (promoted internal `encode` to pub).
DELTA_BYTE_ARRAY ships as decoder-only for now (rare on the write
side). E4+E5 closed the bytes_out gap to Polars from +20% to +12%.

#### CLI v0

`src/cli/query.zig` orchestrates local-file → local-file query.
Self-contained: readFile/createFile/writeAll via raw linux syscalls
(no `Io` vtable churn for a single-shot CLI). Same Args / filter /
projection / codec selection as the lambda handler. Same Timings
struct, same JSON envelope. Local-iteration speed is dramatically
better than `aws lambda invoke` round-trips for encoder/codec work.

`src/cli/main.zig` got a `query` subcommand parallel to `conform`,
with --output/-o, --filter/-f, --columns/-c, --codec.

#### C1 — scan→consumer protocol

Lambda and CLI both had their own decode/filter/encode loop and their
own byte-copy fastpath, with most of the body byte-identical (the only
real difference: where the per-column bytes come from). Refactored into
`src/core/consumer.zig`:

- `RGSrc { bytes, byte_origin }` — whole-RG byte window the consumer
  slices per-column from. Lambda hands in `RowGroupResult.raw_bytes`
  with `byte_origin = rg_byte_start`; CLI hands in the full
  `file_bytes` with `byte_origin = 0`. Same arithmetic both sides:
  `col_off = data_page_offset - byte_origin`.
- `encodeRG` — decode → filter → re-encode → write to `streaming.Sink`.
- `copyRG` — byte-copy kept chunks (or the whole bounding-box span if
  `kept_set = null`) and emit shifted RowGroup metadata.
- `decodeColumnT` — promoted from both call sites' duplicates.
- `Timings` — shared per-phase counters; lambda's outer struct now
  wraps a `consumer.Timings` and adds `fetch_concurrent_ns` /
  `footer_ns` beside it. CLI's the same plus `read_ns`/`parse_ns`.

To make CLI fit, wrapped its output fd in an `FdSink` so the consumer
talks to a `streaming.Sink` regardless of backend.

Net: -499 LoC across the call sites; one new 369-line module. Lambda
main: 1627 → 1349. CLI query: 591 → 367. All 156 unit tests pass,
3/3 integration tests pass, CLI smoke-tests across encoder + projected
fastpath + bounding-box fastpath all produce pyarrow-readable output.

This unblocks C2 — the expression evaluator now has one place to plug
in (the consumer's decode→filter→encode pipeline) instead of having
to wire identical changes into two call sites.

#### C2 — expression evaluator (first slice)

ZPQ can now compute new columns:

```sh
zpq query data/benchmark_100mb.parquet -o out.parquet \
  --select "int8, int8 + 100 AS shifted, int64_sorted * 2 AS doubled, int64_random / 1000 AS thousands"
```

That command stops being "S3-to-S3 lane" and starts being "minimum
useful query engine on Lambda" — the framing I keep landing on.

Three modules in `src/core/expr/`:

- `ast.zig` — typed AST: literals (i64/f64), column refs (resolved at
  parse time so the AST is fully typed), binary arithmetic. Promotion
  rules: any-int → i64, any-float → f64. Two result types keep the
  kernel matrix small.
- `parser.zig` — recursive-descent over a tiny tokenizer. Standard
  precedence (`*` `/` bind tighter than `+` `-`); parens override.
  Identifiers resolve through the file's schema. `expr AS alias`
  captured at the top level.
- `eval.zig` — recursive evaluator. Comptime-specialized kernels per
  (op, T) so the inner loops are straight-line scalar code the
  optimizer can vectorize. Promotion happens at column-ref load
  (i32→i64, f32→f64) and at binop child boundary, so kernels see
  same-typed slices.

The benchmark fixture caught one assumption immediately: every column
in `data/benchmark_100mb.parquet` is OPTIONAL with `max_def=1`, even
the ones that have no actual nulls. The strict "reject if def_levels
is non-null" rule was too tight. Relaxed to "reject if any def_level
< max_def" — O(n) scan, dwarfed by the rest of decode/encode.
Null-aware arithmetic (proper SQL-style null propagation) is a
follow-up; the current behavior is correct for the common case where
writers default-emit OPTIONAL on non-null data.

Wiring on the consumer side:

- `core.consumer.OutputCol` is a new tagged union — `passthrough(ci)`
  or `computed(expr, alias)`. `encodeRG`'s old `kept_in_order:
  []usize` parameter became `output_specs: []OutputCol`. The CLI
  builds it from `--select`; lambda builds it from `kept_in_order` as
  passthrough-only entries (lambda surface for `--select` lands when
  nested-schema splicing is sorted out).
- `encodeRG`'s `filter` param became `?Filter`. When null, the
  selection vector stays all-1s. This dropped lambda's tautology-
  filter hack (the `int64 .GtEq min_int` synthesis used to force the
  encode path on no-filter+nested-projection).
- New `buildSelectSchema` in `cli/query.zig` synthesizes a flat output
  schema for the `--select` path — passthrough copies the input
  leaf's SchemaElement; computed gets a fresh REQUIRED leaf typed
  INT64 or DOUBLE.

Verified end-to-end against `data/benchmark_100mb.parquet`:
- `int8 + 100` matches `src + 100` byte-for-byte (i32 input,
  literal-promoted to i64, kernel runs i64 add)
- `int64_sorted * 2` matches `src * 2` byte-for-byte
- `int64_random / 1000` matches Python's truncating division
- `int64_sorted + 0.5` produces an f64 column with values
  `src + 0.5` (mixed-type promotion path)
- `float64 * 2` stays f64 (no promotion needed)
- `--filter "int8 >= 0" --select "int8, int8 * int8 AS sq"` —
  260963 rows survive, `sq == int8*int8` for all of them. Filter +
  select compose.

180/180 unit tests pass; 3/3 lambda integration tests pass. Encoder
phase shows up cleanly in the per-phase JSON envelope (the existing
instrumentation paid off again — `encode_ms` going up when I add a
computed column is exactly the readout I want).

#### C3 — `BETWEEN`, string concat (`||`), `coalesce`

The first batch of C3 user-facing surface lands. ZPQ stops being
"filter + numeric arithmetic" and starts being "queries you'd
actually write."

**`BETWEEN x AND y`** in the filter parser. The trick was that
`BETWEEN` contains an embedded `AND` that the conjunction splitter
would otherwise grab. `findTopLevelAnd` walks the expression
left-to-right with a counter that bumps on each `BETWEEN` and
decrements on the next `AND`, so `score BETWEEN 0.5 AND 0.9 AND
id=1` parses as `(score >= 0.5 AND score <= 0.9) AND id=1`.
Case-insensitive.

**String concat (`||`)** in the expression layer. Three changes:
- `Type.str` lane added (alongside `i64` and `f64`); promotes only
  with itself, cross-lane mixes return null (parser surfaces
  `TypeMismatch`).
- `'foo'` lex as a string literal token; `||` lex as `pipe_pipe`.
- `concatKernel` allocates per-row joined bytes from the per-RG
  arena. Borrowable optimization deferred until profiling shows it.

Synthesized output leaves carry `converted_type = .UTF8` and
`logical_type = .{ .STRING = .{} }` so pyarrow / polars surface
computed string columns as strings, not raw binary. Caught this on
the first end-to-end run (the smoke test was fine but the schema
showed `binary`).

**`coalesce(col, default)`** as the first user-callable function.
Added a general `Func` enum + `Call` AST node; the parser routes
`IDENT(...)` to `parseCall` which validates arity and arg types.
First-slice scope: 2 args, first must be a column ref, second must
be a literal. The eval kernel walks `def_levels` per row —
`def_level >= max_def` keeps the column value, otherwise emits the
default. Output column is REQUIRED (no nulls). Numeric promotion
through coalesce works (i32 column + i64 default → i64 output).

Verified end-to-end against the benchmark fixture's `int32_nullable`
and `string_nullable` columns:
- 52440 source nulls in `int32_nullable` → all replaced with -999,
  zero remaining nulls.
- 52440 source nulls in `string_nullable` → all replaced with
  `'<missing>'`.

Bonus: unary minus support in the parser landed because `-999` was
the natural way to write the coalesce default. Folds at parse time
for literals, otherwise emits `0 - expr`.

Deferred to follow-ups (when a workload demands them): `case when`
expressions, multi-arg `coalesce` with column-ref tail args, more
functions (`abs`, `length`, `lower`, `upper`).

197/197 unit tests pass; 3/3 lambda integration; CLI smoke tests
across BETWEEN, `||`, coalesce(int), coalesce(string) all green.

#### Warm-path profile + the QUEUE_CAP fix

Following the production reality check, dug into the warm-path gap.
Phase timings showed `put_ms` of ~1700ms with only ~785ms of CPU work
inside it — ~900ms unaccounted. Hypothesis: backpressure or fetcher
starvation.

Added two timings to localize:
- `close_ms` — split out from `put_ms` to isolate "wait for the
  multipart upload tail to ack" from "build the output."
- `wait_for_rg_ms` — wall-clock the drain loop spent blocked on
  `queue.getOne` waiting for the next RG.

Median across 5 runs (balanced workload, before fix):

```
build_ms = 1563ms
close_ms = 690ms
wait_for_rg = 405ms      <-- this
decode = 277ms
encode = 363ms
sink   = 121ms
```

`wait_for_rg = 405ms` — the main task spends 30% of its build time
blocked on the fetcher queue. The smoking gun: `QUEUE_CAP = 1`. Each
file's fetcher could only stage one RG ahead, so by the time the
consumer moved from file 0 to file 1, file 1's 2nd-Nth RGs hadn't
been fetched yet.

Bumped to `QUEUE_CAP = 16`. Now every file's RGs pre-stage during
file 0's processing window. Memory: 10 files × 16 RGs × ~16 MB =
~2.5 GB peak, well within the 5 GB Lambda config.

Post-fix sweep (best of 3):

```
Scenario     zpq before    zpq after    polars
narrow       1149ms        877ms        673ms
selective    1192ms        1070ms       915ms
balanced     1912ms        1735ms       1571ms
broad        2159ms        2140ms       1761ms
```

Improvement: 24% on narrow, 10% on selective, 9% on balanced.
Broad barely moved because its bottleneck is encode time, not
fetch starvation — single-threaded encode of 117 MB output is the
remaining gap. Parallel encode is a follow-up.

Cold-start re-verified: zpq init 16ms vs polars 587ms — **36×
moat preserved**. Cold total 1826ms vs polars 3128ms — 1.7× ahead.
The queue-depth fix didn't regress cold start.

The lesson: **instrumentation closes more gaps than guessing**.
The queue-depth value `1` was an unexamined default written when
the parallel-fetcher design first landed. It looked fine in the
single-file case (where it's optimal), and the production
benchmark that would have caught it never ran for the entire v2
era because of the deploy bug. Without the deploy fix and the
new wait_for_rg counter, this would have stayed hidden.

#### Lessons

1. **Cross-impl validation is the only validation.** A snappy bug
   that round-tripped through our own decoder hid for hours. The
   minute we fed the bytes to cramjam, it surfaced.
2. **Don't preserve ratios on a hunch.** B4's strict-per-file design
   regressed badly; the fix was to keep the *cross-file* fan-out the
   probe had revealed was load-bearing. Probes earn their keep.
3. **Instrumentation pays for itself in one bug.** E4's dict
   threshold mistake would have been undetectable without per-phase
   timings.
4. **Vendoring decode-only libraries is silly when std has them.**
   We pulled zstd compression-side and used std.compress.zstd for
   decode. Smaller binary, less code to own.
5. **CLI parity isn't a bonus — it's an iteration multiplier.** The
   moment the CLI worked, encoder/codec debugging speed went up
   maybe 5×. Should have built a CLI v0 sooner.

### 14:00 — Phase 6.1: multi-file scan, ZPQ wins again

Probed Polars + DuckDB on a 10-file partitioned dataset
(`s3://.../zpq_multi_test/year=2026/month={01..10}/data.parquet`,
each ~15 MB). Polars warm: ~360 ms. DuckDB warm: ~870 ms. ZPQ
status quo (10 sequential single-file invocations): ~1200 ms with
*10 separate output files* — fundamentally a different operation.

Two real bugs surfaced during probe:

- `fix(io/s3): URI-encode keys for SigV4 (handles Hive partition '=')`
  — ZPQ returned 403 SignatureDoesNotMatch on any key with characters
  outside `[A-Za-z0-9-._~/]`. Path canonicalization for the SigV4
  signature must match the HTTP request line; we weren't encoding
  either. Latent bug: every benchmark key we'd previously used had
  only safe chars. Fixed with an `buildEncodedPath()` routed through
  every path-build site.
- (Bigger refactor) The `fetchManyRanges` primitive had baked-in
  assumptions that all ranges came from one (bucket, key) and used a
  shared sparse `into` buffer with absolute file offsets. Generalized
  to `fetchJobs(jobs)` where each job carries its own `(bucket, key,
  range, target)`. The old single-file `fetchManyRanges` is now a
  thin wrapper. This is the primitive that lets one parallel dispatch
  span N files through the same pool.

Refactor of `handleS3Write` to take `[]const []const u8` input URLs
instead of a single URL. Single-file becomes the N=1 case. Per-file
state (`FileSpec`) holds parsed meta, sparse file_buf, survivors[].
The body iterates: per-file metadata fetch → schema validation → per-
file stat-prune → accumulate FetchJobs across all files → one
parallel `fetchJobs` call → per-file decode/filter/encode (or byte-
copy) → unified output footer.

Two new builder functions:
- `fastpath.buildMulti` — concatenates surviving RGs from N files
  byte-for-byte into one output. Single-file `fastpath.build` still
  wraps it.
- `buildFilteredOutputMulti` (in main.zig) — per-file decode + filter
  + encode loop, accumulating into one output buffer. Schema cloned-
  as-required from first file (all inputs share schema by check).

First implementation had **sequential** metadata fetch — 10 files ×
~3 GETs each = ~620ms of fetch time. Total wallclock 700ms. Polars
beat us at 360ms.

Parallelized metadata fetch via `Io.Group.concurrent` (mirrors the
fetchOneTask pattern from s3.zig but with a `MetaFetchCtx` that does
its 2-3 GETs from one acquired pool slot). Median dropped 700 → 300
ms.

Final scoreboard, 10 × 15 MB files, filter `int8>0`, project `int8`,
5 warm runs:

```
                 median_ms   bytes_out
zpq_multi          323        1.0 MB (PLAIN)
polars_multi       364         58 KB (snappy+dict)
duckdb_multi       843        230 KB (snappy)
```

ZPQ wins by 11% over Polars, 2.6× over DuckDB — *despite output 17×
larger* (PLAIN vs Polars's compressed). The warm-pool architecture
again carries the day. Adding snappy/dict encoders (Phase 5.4d/5.4e)
should extend the lead since smaller PUT body shaves another ~50ms.

The dataset axis is now real: ZPQ accepts `inputs: [...]` of N
parquet URLs, validates schemas match, parallel-fetches all metadata,
parallel-fetches all column data through one shared pool, builds one
unified output. The remaining Phase 6 sub-features (partition
pruning, partitioned output, streaming for >1.5 GB, manifest input)
all build on this primitive.

### 10:00 — Phase 5.4b ships: per-row filter encoder, ZPQ wins every workload

Opened with: "if 5.4b ships, ZPQ's positioning becomes 'fastest Parquet
engine on Lambda for *every* workload'". Shipped it. We win them all.

Realized while planning the integration: today's 5.1/5.4a code doesn't
just *underperform* on value-level filters — it produces *wrong*
output. When the user passes filter `int8 > 0`, ZPQ stat-prunes at the
row-group level (no RGs prune since [-128, 127] overlaps `> 0`), then
copies whole row groups. Result: every row of every RG, including
ones with int8 ≤ 0. Polars/DuckDB on the same input return ~half the
rows (the positive ones). 5.4b closes both the perf and *correctness*
gap.

src/core/writer/encoder.zig (new, ~250 LoC) — PLAIN encoder for all
six physical types:
- encodePlainTyped<T> for INT32/INT64/FLOAT/DOUBLE: little-endian
  fixed-width writes.
- encodePlainBytes for BYTE_ARRAY: `<u32 LE len><bytes>` per value.
- encodePlainBool: bit-packed LSB-first.
- encodeColumn ties value encoding + page-header thrift +
  ColumnMetaData. Single page per chunk, codec=UNCOMPRESSED.
- applySelection: materialize the filter-surviving subset of a typed
  Batch.Column slice in `arena`.
- statsTyped/statsBytes/statsBool compute min/max from surviving
  values; no null tracking yet.

src/lambda/main.zig: new buildFilteredOutput function (~150 LoC) that
implements the decode-write path:
1. Compute fetch_set = filter_cols ∪ kept_cols.
2. Per surviving RG: range-fetch the needed columns, decode each via
   ColumnChunkReader<T>, build a Batch, evaluate filter -> sel.
3. For each kept column in input order: applySelection, encodeColumn,
   patch absolute file offset on data_page_offset, append bytes.
4. Build new schema (cloneSchemaAsRequired forces leaves to REQUIRED
   since the encoder doesn't emit definition levels — semantically OK
   because filter survivors are never null).
5. Serialize footer thrift, append, append footer-len + PAR1.

handleS3Write dispatches: filter present → buildFilteredOutput;
no filter → existing fastpath.build (byte-copy + projection).

Range-fetch logic also updated: with filter, fetch (filter cols ∪
kept cols) — both needed (filter cols for evaluation, kept cols for
output).

First-cut limitations:
- PLAIN encoding only (output 4-5× larger than snappy-compressed).
- Single page per column (no multi-page chunks).

### 09:00 — Persistent pool wins all three benchmarks

Pushback from earlier ("you don't get to call it 😄") drove a deeper
look at why DuckDB was beating us by ~140 ms on projection. Argued
against jumping to eBPF/local-DuckDB profiling (different network,
different env) and pushed for instrumenting ZPQ itself first.

Added per-phase trace prints inside handleS3Write. Run 2 (warm) of
projection, before this commit:

Smoking gun: every "acquire" was 33-50 ms, which IS the TLS handshake.

the separate `s3.Client` instance that also paid its own handshake
per invocation).

connections. First implementation tried 1 retry; that wasn't enough
because the FIFO queue cycles through stale slots before reaching
freshly-init'd ones. Bumped retry to POOL_SIZE+1=9 — guaranteed to
drain stale slots in the worst case. Applied uniformly across
getViaPool, putViaPool, fetchOneTask, uploadPartTask.

### 06:00 — Read parallelism + connection pool, probes confirmed design

Two probes (committed but reverted before build):

- Probe 1 (no filter, all 4 RGs survive): `coalescer: 4 input ranges
  -> 1 merged range`. We were fetching one giant 148 MB range in a
  single GET at ~31 MB/s. Pure bandwidth waste — the writer-side
  parallelism we shipped in 5.3 didn't help here because the reader
  was bottlenecked upstream.
- Probe 2 (filter keeps non-adjacent RGs): `2 input ranges -> 2 merged
  ranges` (38 MB gap > 64 KB COALESCE_GAP). Per-range throughput
  varied wildly (24-51 MB/s) — parallelism would smooth that out.

These together justified the unified design: same `Pool(N)` +
`fetchManyRanges` primitive serves both "split one big range into N"
and "fetch N existing ranges in parallel." Pool is the concurrency
budget; with HTTP/1.1 a connection is a permit, so one queue gates
both reads and writes.

Built `src/io/pool.zig` (~120 LoC). Backed by `Io.Queue(usize)` over
slot indices — getOne blocks naturally when the pool is saturated,
no custom Mutex+Condition. Lazy connection init on first acquire of
each slot. A self-referential struct gotcha bit me: returning a Pool
by value invalidates the Queue's slice into `self.free_buffer`. Fixed
with in-place init (`pub fn init(self: *Self, ...) !void`).

`s3.fetchManyRanges` splits any range > 24 MB into ~19 MB sub-ranges,
dispatches all jobs through `Io.Group.concurrent` bounded by the
pool. Refactored `s3.uploadMultipart` to acquire from a pool too —
both phases of one Lambda invocation share the same 8 pre-warmed
connections when input bucket == output bucket (typical case).

Benchmark numbers, 5120 MB Lambda, warm runs:

```
                       before pool    after pool   speedup
ZPQ copy fetch_ms     ~5300         ~700         ~7.5x
ZPQ copy put_ms       ~870          ~810         ~same (already pooled-ish)
ZPQ copy total_ms     ~3107         ~1700        ~1.8x
ZPQ prune-all total   ~183          ~180         no change (no parallel reads)
```

Per-stream throughput on Lambda 5120 MB: ~24 MB/s × 8 parallel ≈ 192
MB/s (bakeoff predicted), measured 200 MB/s — within noise.

Updated head-to-head:

```
                ZPQ           Polars      DuckDB     boto3
Copy 155 MB    ~1700 ms ⚡   ~2000 ms     ~3000 ms   ~3000 ms
Prune-all       ~180 ms       575-2900 ms  125 ms ⚡  n/a
```

ZPQ now wins copy (was the headline weakness from previous benchmark).
Loses prune-all to DuckDB by ~55 ms — likely httpfs HTTP/2 multiplex
or smaller range fetches; not worth chasing yet.

What this validated structurally:

- One `Pool(N)` primitive is the right shape — same code path for
  splitting one big range AND for fetching many existing ranges
  (Phase 5.4 column-projection workloads will exercise the second).
- Type-erased dispatch through `*anyopaque` + function pointers lets
  `fetchManyRanges` and `uploadMultipart` consume any `Pool(N)`
  without comptime-specializing each consumer per N.
- `Io.Queue` was the right primitive — naturally blocks on full,
  natural FIFO recycling, no homegrown synchronization.

The HTTP/2 probe (deferred during this session) is now slightly more
interesting: if HTTP/2 multiplex on one connection beats HTTP/1.1+pool
on many small ranges (Phase 5.4 territory), that's the next architectural
question. Not gating anything immediate.

### 02:15 — Two latent thrift round-trip bugs surfaced by fastpath

Writing `core/writer/fastpath.zig` (byte-copy + footer rewrite) exposed
two bugs in shared thrift-write infrastructure that nothing had
exercised before:

- `thrift.Writer.writeStructBegin/End` reset `last_field_id` to 0 on
  begin (correct, so the inner struct gets its own delta-encoding
  namespace) but never restored the outer's `last_field_id` on end.
  Subsequent outer fields then computed deltas from a stale value
  (the inner struct's last field id), so e.g. writing `data_page_offset`
  at field 9 after a nested `Statistics` struct produced a delta that
  the reader interpreted as field 11 (`dictionary_page_offset`). The
  result: data and dict offsets *swapped* on round-trip. Our reader
  code never tripped this because we hadn't been writing thrift bytes
  back out.

  Fix: writer now keeps a small stack of saved `last_field_id` values,
  pushed on `writeStructBegin` and popped on `writeStructEnd`. Stack
  depth 8 is plenty for Parquet metadata (max nesting we hit is ~3).
- `schema.zig` was writing `Statistics` at thrift field id 8 instead
  of 12. Per `parquet.thrift`, field 8 is `key_value_metadata`; 12 is
  `statistics`. Our reader handled 8 as skip, so stats were silently
  lost on every round-trip through `FileMetaData.write`. Combined
  with the bug above, this is the first version of the writer where
  stats actually round-trip.

Both fixes land independent of the fastpath feature — they were latent
bugs waiting for the first writer to exercise them.

### 01:30 — Phase 5.1 research turned up no comparables

Looked at how DuckDB, Polars, Hardwood, and Parx handle Parquet
output. None of them have ZPQ's "filter row groups, copy bytes,
renumber footer offsets" fast path. They all re-encode through their
own column-writer abstractions (`extension/parquet/parquet_writer.cpp`,
`crates/polars-parquet/src/parquet/write/file.rs`, etc.). That
makes sense — they're general-purpose engines that need a writer
hot path for arbitrary materialized output. We're an ETL tool that
wants `cp` semantics when the query is identity-on-row-groups.

So this phase is a place where we genuinely don't have prior art to
crib from. The algorithm is:

- Walk surviving row groups in order.
- For each, find its byte range
  `[min(dict_offset, data_offset), data_offset + total_compressed_size]`
  across columns.
- Append those bytes to the output buffer at `new_pos`.
- Update each column's `data_page_offset` and (if present)
  `dictionary_page_offset` by `new_pos - old_start`.
- Drop page index + bloom filter offsets (set to null) — those point
  to bytes outside the row-group region and we don't carry them
  forward in the fast path. Downstream readers fall back to
  row-group-level pruning. Re-add later if a benchmark wants them.
- Re-serialize the (mutated) `FileMetaData` via `thrift.Writer`.
- Output: `[PAR1][rg bytes][...][footer thrift][u32 LE footer-len][PAR1]`.

The plumbing we need is already in tree: `core/thrift.zig` has
read+write, `core/schema.zig` has `FileMetaData.write` and
`RowGroup.write`, `core/parquet/metadata.zig:open()` parses, and
`core/filter/*` produces the surviving-row-group bitmask. So the
new code is small — a single `core/writer/fastpath.zig` that ties
those together.

### 00:00 — `Io.Threaded` settles the writer substrate question

Going-in question (per `docs/writer_design.md` revised earlier this
session): writer uses `std.Io.Threaded` + `Io.Group`, or wire our
in-tree epoll loop into the S3 stack? Three options were on the table:
full `std.Io` port (delete loop), hybrid (loop for reads, threads for
the writer), or keep loop and build our own `InFlight(N)` mirroring
`Io.Group`'s shape. Design doc favored the hybrid a priori but flagged
"we'd have to test the loop to know it isn't even worse than threads."
Cheap-falsification path: build the threaded probe first, only invest
in the loop variant if threads fall short.

Built `probes/bakeoff_threaded`. Real S3 multipart upload of a 155 MB
payload as 8 × ~19 MB parts. Each task does its own DNS + handshake —
pessimistic, no pooling. Caller code for the parallel dispatch is
~10 lines (`Io.Group` + `group.concurrent` in a for loop, then
`group.await`).

Real bugs found along the way:

- `fb33d6a` — `src/io/http.zig` had no chunked-transfer support.
  S3 returns `Transfer-Encoding: chunked` on multipart-control
  responses (Create / Complete) with no `Content-Length`. Our
  drainResponse was reading until connection-close, which on S3 takes
  ~6s. Each multipart upload was paying ~12s of pure overhead. Reader
  code never tripped this because GETs always carry Content-Length.
- TLS partial-write — `src/io/tls.zig:Connection.send` treated
  `consumed == 0` as a hard failure. With ~MB-sized plaintexts,
  BoringSSL's `SSL_write` hits BIO back-pressure mid-stream and
  returns 0 + `WANT_WRITE` ("drain encrypted bytes, then I can take
  more"). On dev box this rarely triggered because residential
  bandwidth was so slow the BIO never filled; on Lambda's faster pipe
  it bit immediately. Fix: tolerate `consumed == 0` if encrypted bytes
  were drained. Also enabled `SSL_MODE_ENABLE_PARTIAL_WRITE` in
  `vendor/boring_tls` so SSL_write returns positive byte counts as it
  makes progress through the buffer.
- `Io.Group.async` vs `.concurrent` — `async` runs synchronously when
  the worker pool is saturated (default `cpu_count - 1`). We thought
  we had 8 parallel uploads on Lambda but were getting 1 worker
  thread + 7 deferred. Switched to `.concurrent` which guarantees
  parallelism (or `error.ConcurrencyUnavailable`).

Lambda data, warm runs, 4 invocations per tier, fresh keys:

| Memory   | par best/worst | MB/s best/worst | % of 5 Gbps |
| -------- | -------------- | --------------- | ----------- |
| 256 MB   | OOM            | —               | —           |
| 512 MB   | ~5.4s          | ~28             | ~5%         |
| 1769 MB  | 0.97 / 1.39s   | 160 / 111       | 18-26%      |
| 3008 MB  | 0.77 / 1.56s   | 201 / 99        | 16-32%      |
| 10240 MB | 0.62 / 2.85s   | 248 / 54        | 9-40% var   |

Throughput scales with memory tier — that's CPU saturation, not
network. Lambda meters CPU by memory tier, more memory = more vCPUs =
more parallel TLS encryption. No tier hits even half of 5 Gbps. At
10240 MB we crest at ~40% of theoretical. Variance at higher tiers
(10240 MB best/worst 0.62 / 2.85s) is real but probably S3 burst
throttling on rapid-fire fresh keys or cross-AZ jitter — not a
substrate property. Not investigating further now.

Despite not network-saturating, `Io.Threaded` is the right call.
An event loop is single-threaded by construction; it cannot
parallelize CPU-bound encryption across cores. At every tier with
>1 effective vCPU, threads win. The only tier where this might be
different is 256 MB, and we OOM there anyway. So no `bakeoff_epoll` —
the result is predictable from first principles.

The more interesting question that's now open: how do we get from
~250 MB/s to 500+ MB/s at the high tiers? Levers worth checking
post-5.1:

- Confirm BoringSSL is using AES-NI / ARM crypto extensions on
  Lambda's Graviton2. If not, that's the biggest available win.
- Reuse TLS sessions across the 8 parts (tickets / resumption).
  Eliminates 7× handshake cost. Probably small impact since
  handshake is ~50ms and parts take 1-3s, but cheap to verify.
- Tune `Io.Threaded.async_limit` higher than `cpu_count - 1`.
  One-line experiment.

None block the writer phase. Decision: adopt `std.Io.Threaded` +
`Io.Group.concurrent` as the writer concurrency primitive. Hybrid
model — in-tree loop stays for reader-side I/O (shipped, fine);
threads for writer parallelism. `docs/writer_design.md` updated to
reflect "decided" rather than "recommended pending data."

### 16:14 — Phase 6.2 plan: partition pruning

Researched prior art for path-based partition pruning before writing
code. Findings:

- **Our own tree**: `tests/integration/test_partitioned_passthrough.zig`
  exists in `main` and a few other branches but not `v2-sans-io`. It's
  a demo with hardcoded `region=us`-style paths — no actual pruning
  logic to crib. Discard.
- **Polars** (`polars-io/src/hive.rs`): `materialize_hive_partitions`
  treats partition values as `ScalarColumn`s injected into the frame.
  Optimizer then folds filter→constants. Works but heavy machinery
  for our shape.
- **DuckDB** (`src/common/hive_partitioning.cpp`): cleanest pattern.
  `HivePartitioning::Parse(filename)` walks the path linearly, splits
  on `/`, captures `key=value` segments into a `map<string,string>`.
  `ApplyFiltersToFileList` copies each filter, replaces partition col
  refs with constants via `ConvertKnownColRefToConstants`, evaluates;
  if scalar-foldable to false → drop the file. Filters that can't be
  resolved purely from partition cols are preserved for the data path.
- **Hardwood**: nothing.

**ZPQ shape**: our `Filter` AST is keyed by `col_idx` in the file
schema. Partition columns aren't in the file schema, so we can't
encode them as `Filter` leaves directly. Two paths:

1. Parse twice — once as a partition-only predicate (col-name keyed,
   string values, evaluated against the path's `key=value` map), once
   as the data filter (existing parser, unchanged). Files that fail
   the partition predicate are skipped before metadata fetch.
2. Bolt partition cols onto the file schema as virtual leaves, parse
   once. Looks unified but means every downstream consumer of the
   schema (metadata lookup, projection, encoder) has to know which
   indices are virtual and special-case them. More code, more edges.

Going with #1. Closer to taco-bell — partition pruning is a separate
narrow primitive that runs before the data path, doesn't need to
co-exist inside the AST.

**Plan**:
1. New module `src/core/filter/partition.zig`:
   - `parsePath(url) → []KV` — DuckDB's linear walker, ported.
   - `parsePredicate(arena, expr_text, partition_keys) → ?Predicate`
     — accepts only AND-of-leaves where every leaf's column is a
     partition key. Returns `null` if any leaf references a non-
     partition column (signals: don't try to prune, run normal path).
     String-typed values; numeric coercion done at eval time if the
     value parses as int/float.
   - `eval(predicate, partition_kv_map) → bool`
2. In `handleS3Write` (multi-file path):
   - For each input URL, parse the path partitions.
   - Collect the union of partition keys seen across all URLs.
   - If `filter_sql` provided, attempt partition-only parse against
     that key set. If successful, evaluate per-file → mark survivors.
   - Skipped files: never enter `MetaFetchCtx`, never get a footer
     fetched. Drop straight out of the survivor list.
   - Surviving files: run today's path (parallel meta fetch, etc).
3. The "filter" passed to data-path stays the same — partition leaves
   stay in the text. Today's parser will fail to bind them
   (UnknownColumn). For phase 6.2 v1, we tolerate this only when the
   *whole* filter is partition-only (then data filter = empty →
   fast-copy path triggers). Mixed filters (partition AND data) come
   in 6.2.1: strip partition leaves from the text before handing to
   the data parser.

**Probe before implementing**: build a 10-file fixture
`s3://.../zpq_test_data/partitioned/year=2026/month={01..10}/data.parquet`
(each ~10 MB, schema-compatible with our existing test data), then
measure:
- Baseline (no filter): 10 files copied → wallclock = 10×single-file.
- Partition-only filter `month >= 08`: only 3 files survive.
  Expected after Phase 6.2: ~3× single-file time (no metadata fetch
  for the 7 skipped files). Today: 10× (we'd fetch all 10 footers).
- Polars + DuckDB on the same scan to confirm they prune.

That's the contract: 70% reduction in wallclock for a filter that
prunes 70% of files. Linear with prune rate.

### 17:22 — Phase 6.2 results: partition pruning ships, narrow win

Implementation: `src/core/filter/partition.zig` + 60-LoC wedge in
`handleS3Write`. Files whose path-encoded partition values fail the
filter are dropped before any S3 IO — no metadata fetch, no footer
parse, no per-file pool acquire. v1 only handles "filter is entirely
partition-only" (parsePredicate returns null on any non-partition
column → falls through to today's code).

Workload: 10 hive-partitioned files
(`year=2026/month={01..10}/data.parquet`, ~14 MB each), filter
`month >= '08'` ⇒ 3 files survive. 5120 MB Lambda, x86_64, warm.

```
                pruned (3/10)   copy-all (10/10)    speedup
zpq:partprune   873-1161 ms     (n/a — bug)         —
polars          968-1118        1760-2075           1.75x
duckdb (glob)   1198-1423       2730-4383           2.28x
```

ZPQ medians ~926 ms. Polars ~1064 ms. DuckDB ~1247 ms.

**The expected dominance didn't show up.** Why ZPQ isn't running away
with this:

- Polars and DuckDB **also** path-prune when `hive_partitioning=true`

  and skip files whose constants don't satisfy the predicate. So all

- Partition pruning works end-to-end (7 files dropped pre-IO).
- ZPQ still wins both head-to-heads (~13% over Polars, ~26% over

  the same algorithmic trick.
- The 1.75x / 2.28x speedups vs the engines' own copy-all confirms
  pruning is effective on both sides.

**Rough edges found, not fixed in this slice:**
- 10-file no-filter copy returns `InvalidColumnOffsets` from

  cumulative-offset bug in the multi-file fast path, surfaced by the

- DuckDB 1.4.3 with `read_parquet([explicit list], hive_partitioning=true)`

  Their bug, not ours.
- Polars infers partition values as i64; DuckDB infers as VARCHAR.
  Filter syntax has to differ per engine (`month >= 8` vs

- Prune ratios are extreme (1 of 1000 files surviving, not 3 of 10).

### 17:42 — Bug hunt: pointer-to-stack-local in multi-file fastpath wiring

The "InvalidColumnOffsets at N=10" lurking from the 6.2 bench wasn't
in fastpath.zig and wasn't a concurrency race. Two false trails before
the real one:

1. **First false trail — bad test harness.** I'd been generating the
   N=10 input list with
   `printf '"s3://%s/.../month=%02d/data.parquet",' "$BUCKET" $(seq 1 10)`.
   printf cycles args: pair 1 was `(BUCKET, 01)` correctly, pair 2 was
   `(02, 03)` — i.e. "02" became the bucket. The second URL was
   `s3://2/...` and on. Most invocations hit cross_bucket_inputs error
   for that reason; sometimes they got farther with corrupted keys
   that S3 rejected. Once I switched to `printf '"%s",' "${INPUTS[@]}"`
   with a proper bash array, the payloads were honest.
2. **Second false trail — concurrent ArenaAllocator.** With clean
   payloads, InvalidColumnOffsets reproduced deterministically. My
   first hypothesis was that the meta-fetch tasks shared `ctx.arena`
   (the per-invocation arena) and ran on real OS threads via
   `Io.Threaded`; concurrent bump-pointer allocations would clobber.
   Plausible. I made the change (per-task arena, owned by gpa,
   deinit'd at end of handleS3Write) and redeployed. Same exact
   error, same exact bytes. Real concurrency bugs are flaky; this
   was deterministic. Wrong hypothesis.

The actual bug, in the multi-file fastpath dispatch:

```zig
var fp_specs = try a.alloc(fastpath.FileSpec, specs.len);
for (specs, 0..) |sp, i| fp_specs[i] = .{
    .bytes = sp.file_buf,
    .meta = &sp.meta,        // address of a STACK-LOCAL copy
    .survivors = sp.survivors,
};
```

`for (specs) |sp|` iterates by value — `sp` is a copy of `specs[i]`
that lives in a stack slot reused across iterations. `&sp.meta`
captures the address of that local slot. By the time fastpath reads
`fp_specs[2].meta.row_groups`, `sp` has long since been overwritten
by later iterations or unrelated stack frames; the dereference
returns whatever bytes happen to be there.

That perfectly explained the eerie debug output:
`file#=2 range.len=14142954 (≈ month=02's content size) num_rows=52436 (= month=10's row count)`.
The pointer was dangling and finding garbage that happened to look
like row-group fields from various neighbouring stack frames.

**One-character fix:** `for (specs, 0..) |*sp, i|` (by reference).
Now `&sp.meta` is `&specs[i].meta` — stable across the loop and into
the fastpath call.

Why N=3 worked and N=10 didn't: with fewer iterations the stack slot
holding `sp` *might* still happen to contain coherent bytes by the
time fastpath ran (probably because the slot still held the last
iteration's value and fastpath only looks at `fp_specs[N-1].meta`
last). At N=10 something about the stack churn / register-allocator
choices in ReleaseSmall flipped the dice the other way. Classic
undefined behaviour: works by accident at small scale, fails by
accident at larger scale. Don't trust either reading.

I kept the per-task arena change too. It wasn't the culprit but
ArenaAllocator across `Io.Threaded` workers genuinely is unsafe and
would've bitten us under a different access pattern.

Numbers after the fix, 5120 MB Lambda, x86_64, warm, 5 runs, median:

```
                    partprune (3/10)  copyall (10/10)
zpq                 857 ms            1732 ms
polars              973 ms            1795 ms
duckdb              1316 ms           2717 ms
```

ZPQ now wins both — including the previously-broken copy-all case.
The copy-all win is satisfying: ZPQ writes 141 MB (PLAIN, byte-copy
through), Polars writes 117 MB (snappy re-encoded), DuckDB 140 MB.
Outputting more bytes and still finishing first means the byte-copy
fast path beats Polars' decompress-recompress even when Polars saves
~17% on bytes-uploaded.

**Lessons:**
- Verify the harness before chasing the code. Cost me ~30 min.
- Deterministic ≠ logic bug. Could still be UB-deterministic
  (stack reuse, register allocation, etc).
- Iterate by reference whenever you take an address. This Zig pattern
  bites identically in C, C++, Rust (well — Rust's borrow checker
  catches it). One of the few cases where Zig's "you're an adult"
  philosophy lets you walk into a buzzsaw. Lint candidate.

### 19:14 — Phase 5.4c-ish: nullable parity + an emergency wire-correctness fix

Set out to add nullable-column support for tonight's bench. Delivered:

1. **RLE/bit-packed-hybrid encoder** (`hybrid_rle.encode`): pair to the
   existing decoder. For all-1s def levels (the common case for
   surviving filter results) it emits a single ~3-byte RLE run. Mixed
   inputs use bit-packed groups of 8 with leftover trailing values
   emitted as 1-element RLE runs (since bit-packed runs cannot have
   partial groups — the decoder has no way to distinguish padding
   from real values, learned the hard way via a failing test).
2. **Encoder emits def-level prefix** for OPTIONAL leaves: a `<u32 LE
   byte_len><RLE bytes>` block before the PLAIN values.
3. **Schema honesty**: replaced `cloneSchemaAsRequired` (which lied
   about output nullability) with `cloneProjectedSchema` that
   preserves the source `repetition_type`.

Then the bench validation revealed the bigger problem.

**Pre-existing wire-correctness bug.** Tried to validate the new
output with `pyarrow.read_metadata` — got "Couldn't deserialize
thrift: Invalid data". Bisected (revert nullable preservation, force
REQUIRED encoder) — still broken. Tried byte-copy fastpath — also
broken. So this wasn't from my nullable changes; ZPQ-written parquet
files have NEVER been readable by pyarrow or DuckDB.

**Why nobody noticed:** Polars is permissive about thrift type
mismatches. The benchmarks compared wallclock + bytes_out and never
opened the output files with a strict reader. So we had a fast
output that strict readers rejected as malformed.

**The bug:** `IntType.bitWidth` is defined as `i8` in the
parquet-format thrift IDL. We were writing it with the I32 type
marker (compact thrift type=5, value zigzag-encoded). Strict readers
validate field types against the IDL and reject on mismatch.
Hex-diffing an output footer against the source revealed a single
byte differing 30 bytes into the schema list — `13` (BYTE type
marker) in the source, `15` (I32) in our output. From there it was
obvious: the writer needed a `writeFieldI8` helper that writes the
raw signed byte (compact thrift i8 is NOT zigzag-encoded — special
case in the spec, distinct from i16/i32/i64).

After: pyarrow and DuckDB read every output cleanly. Including
nullable schemas — with all 27 columns marked `nullable=True` in the
output, matching the source.

```
verify byte-copy:    pyarrow OK rows=524288 cols=27 nullable=27
                     duckdb  OK rows=524288
verify filter+proj:  pyarrow OK rows=258818 cols=2  nullable=2
                     duckdb  OK rows=258818
```

What's NOT yet done (deferred to v1.5):
- Source-side decode of actually-null values: the existing decoder
  skips def levels and treats every row as present. Densely-populated
  source columns work; columns with real nulls (e.g. `int32_nullable`,
  `string_nullable`) cause `ShortDecode` because the PLAIN bytes
  contain only `non-null-count` values but the decoder reads
  `total-count`. Detected via filter+all-cols on partitioned fixture
  (one-third of source columns have actual nulls).
  Workaround for tonight: project around the actually-null columns.

Tonight's bench can include:
- Cold-start measurements (deferred, the original plan)
- Output validity (we now satisfy strict readers)
- Honest nullable schema preservation
- Larger workloads with arbitrary parquet inputs that have OPTIONAL
  schemas but no actual nulls in projected columns

**Lesson:** "we run faster" is meaningless if the output is
unreadable. Should have been validating with pyarrow/duckdb from
day 1. Adding that to the standard bench script next.

### 19:50 — Nullable v1 done correctly, hardwood-style

Decode + filter + encode all null-aware. The implementation lifted
its shape from `references/hardwood/` — specifically the
`FlatColumnWorker` / `Page.IntPage` pattern where each typed page
carries `(values, definitionLevels, maxDefLevel)`. Hardwood's
`PlainDecoder.readInts` does the trick we needed: count `numDefined`,
read exactly that many values from the wire, write them only at
slots where `defLevels[i] == maxDefLevel`. Other slots stay at
primitive default.

We kept the per-encoding decoders (PlainDec, RleDictDec, …) unchanged
and put the def-level math one layer up in `ColumnChunkReader`. New
entry point `decodeWithLevels(values, def_levels)`; the original
`decode(values)` now asserts max_def == 0 (caller bug if you forget).

Spread algorithm worth pinning: when a page has N values with K
non-null, we ask the per-page decoder for K packed values into the
front of the output, then walk back-to-front scattering them into
their correct slots based on def_levels. No temp buffer needed —
back-to-front means we never overwrite a packed value before it's
been read. Same trick Hardwood uses inline; just expressed at a
slightly different layer.

Filter eval implements SQL three-valued logic via a tiny `rowIsNull`
inline: any predicate touching a null row deactivates the row in
the SelectionVector regardless of the comparison. Means filter
*survivors* are guaranteed non-null on the columns the filter
touched — but columns projected through that the filter *didn't*
touch keep their source nulls.

Encoder honours both shapes:
- All-1s def_levels (filter-touched columns whose survivors are
  fully present) → tiny RLE encoding (~3 bytes regardless of N).
- Mixed def_levels (projected-through nullable columns) → real
  RLE/bit-packed-hybrid encoding via `hybrid_rle.encode`.

PLAIN bytes contain only non-null values — the decoder side
recovers nulls from def_levels alone. Stats min/max skip null
positions.

**One footgun caught en route.** The first deploy of the new
encoder segfaulted on Lambda for any string column with real
nulls. `ReleaseSafe` build with stack trace pointed straight at
`thrift.writeFieldString` doing memcpy from a stale slice. Cause:
`statsBytes` was returning `[]const u8` borrows into the source
values, and the source values lived on the row-group-scoped
arena that gets `deinit`-ed at the end of each row group's
block. By the time the file footer was written (after all
row-group blocks), those slices dangled. Fix: `statsBytes`
takes the encoder's arena and dupes min/max into it. Numeric
stats already alloc onto `std.heap.page_allocator` (a leak, but
not a dangle — different problem for another day).

End-to-end checks against the partitioned fixture (which has
~10% real nulls in each *_nullable column):

```
filter int32_nullable>0, project [int8, int32_nullable]
    → 235396 rows survived, 0 nulls in output (filter dropped them)

filter int8>=-128 (matches all), project [int8, int32_nullable, string_nullable, float64_nullable]
    → 524288 rows survived, 52440 nulls in each *_nullable column
      (matches source 10% null rate exactly)
```

Verified with both `pyarrow.read_metadata` and `duckdb.read_parquet`.
DuckDB's `count(col)` on the nullable columns returns 471848 = 524288
- 52440 — null counts match across the full pipeline.

What I considered using from Zig 0.16 but skipped:
- `std.MultiArrayList` for SoA values+def_levels: not worth the
  churn. Parquet's wire format hands us the two streams separately
  anyway, so flattening into one and re-splitting at encode time
  is just churn.
- `std.bit_set` packed null mask: 32× memory saving over `[]u32`
  for `max_def == 1`. Real but premature; hardwood uses int[]
  for the same reason. Future optimization.
- `std.Io.Reader` / `Writer`: overkill for in-memory page
  decoding.

148/148 unit tests + 3/3 lambda integration tests green. v1 ships.

### 21:17 — B1a: STRUCT-of-primitive read support (one-line pivot, plus path fixes)

The user pushed back on my "B2 first" instinct: said try B1, fall
back if it doesn't land. I'd been treating B1 as monolithic and
multi-week, but there's a real vertical slice in here.

**Insight:** Parquet's def-level semantics for STRUCT-of-primitive
are *identical* to flat OPTIONAL at the leaf level. A row's leaf
value is "null" iff `def_levels[i] < max_def`, regardless of
whether the column is `optional int32` (max_def=1) or
`optional struct { optional int32 }` (max_def=2). The bit_width
for RLE-decoding levels is `ceil(log2(max_def+1))` and our
existing decoder already uses that. The back-to-front scatter
algorithm we shipped this afternoon also already handles arbitrary
max_def values.

The only thing blocking STRUCT support was a hard `max_def > 1`
assertion in `installDataPageDecoder`. **Lift one assertion** and
struct columns decode.

LIST and MAP are different — those need `max_rep > 0`, meaning a
row can produce multiple leaf values, meaning the flat `[]T`
output shape doesn't fit. That's the *next* slice (B1b).

CLI's `conform` tool both built single-element paths from
`schema.items[ci+1].name` for `getColumnLevels`. For nested

"b_c_int"]`), and the single-element lookup returned `max_def=0`

The user pushed back hard: don't ship a "half-baked" gate that

edge-case fixture wasn't validating the encoder rep-path — it was

**The fixture.** `data/nested_edges.parquet`: 20 rows × 6 columns
deliberately covering empty lists, null lists, lists with internal
nulls, single-element lists, 50-element lists, struct-of-primitive
with mixed nullability, list-of-struct (multiple leaf columns
sharing rep structure), and `MAP<string, int32>`. 9 column chunks
total, each tagged for a specific edge case. Generated via
`tools/gen_nested_fixture.py`, uploaded to
`s3://.../zpq_test_data/nested_edges.parquet`. Decode passes
(`zpq conform` shows ok on every leaf, including 79 leaves of
tags, 72+72 leaves of events, 25+25 of counts).

**What the round-trip stress test revealed.** Every filter+encode
scenario through Lambda failed with `UnsupportedType`. Tracing it
out: the encoder's call site was `meta.schema.items[kept_ci + 1]`
where `kept_ci` is a column-chunk index. For flat schemas this
points at the leaf SchemaElement. For nested schemas the schema
list has interleaved GROUP nodes, so `schema[ci+1]` is no longer
the matching leaf — it's whatever DFS-position the `ci+1`th item
happens to be (often a GROUP, which has `type = null`, hence
`UnsupportedType`).

I patched that (use `meta.getColumnSchema(path_in_schema)` to look
up the real leaf), but then the next layer down was also broken —
in fact, broken in a *worse* way:

**`metadata.findColumnIndex` is fundamentally wrong for nested
schemas.** It iterates `schema.items[1..]` and increments
`leaf_idx` for every node, treating GROUPs as if they were leaves
with column chunks. So:

- `findColumnIndex("tags")` returns `leaf_idx = 2` because "tags"
  is the third schema item. Column chunk 2 is `tags.list.item`.
  Lucky alignment — the user said "tags", they got the right data.
- `findColumnIndex("meta")` returns `leaf_idx = 5`. Column chunk 5
  is `events.list.element.ts`. **Silent wrong column.** The user
  said "meta", they got events timestamps.
- `findColumnIndex("events")` returns `leaf_idx = 8`. Column chunk
  8 is `counts.key_value.value`. Silent wrong column.

This affects every nested-projection code path — including the
byte-copy fastpath when the user supplies `columns: [...]`. We've
been silently producing wrong outputs for nested projections any
time the lookup-by-position alignment didn't accidentally match.

The reason our `list_columns.parquet` byte-copy demo earlier
"worked" was that the call had no projection (`columns` field
absent), so `findColumnIndex` was never called — every chunk
copied through.

**Beyond findColumnIndex, the issues compound:**

1. **User-facing column names don't map 1:1 to column chunks.**
   "events" the user says is a top-level group with TWO leaves:
   `events.list.element.ts` and `events.list.element.code`.
   "Project events" must resolve to *both* chunk indices. Today's
   resolver returns one index (and the wrong one).

2. **`cloneProjectedSchema` builds output schema as
   `[root, src.items[i+1] for i in kept]`.** For a kept set of
   leaf chunk indices that sits inside nested structures, this
   throws away the GROUP ancestors. The output schema lacks the
   `tags` group, `tags.list` group — just the leaf, which won't
   reassemble into a list on the reader side.

3. **MAP/LIST require specific schema shapes** with `repetition_type
   = REPEATED` on the inner group, and certain `LogicalType` /
   `ConvertedType` annotations (`LIST`, `MAP`, `MAP_KEY_VALUE`).
   Building a wire-correct nested output schema means understanding
   parquet's logical-type conventions.

4. **Encoder rep-path is correct in isolation but unreachable.**
   The `filterColumnNested` and rep-prefix code from this session
   would produce correct bytes if called with a proper nested
   ColumnT and matching schema element. It's just not called from
   any code path today — the projection layer corrupts before the
   encoder gets a chance.

**What real B1 actually needs (revising the roadmap):**

- **B1.x: nested-aware column resolution.** Replace `findColumnIndex`
  with a function that returns a *set* of column-chunk indices for
  a user-supplied top-level path. Walk the schema in DFS;
  enumerate chunks under each top-level group.

- **B1.y: nested-aware schema projection.** Given a set of kept
  chunk indices, build the output schema by walking the source
  schema DFS and including every node on the path from root to
  any kept leaf — including GROUP ancestors and their LogicalType
  / ConvertedType annotations. Emit correct
  `repetition_type = REPEATED` on the inner group of LIST/MAP.

- **B1.z: column-chunk-set-aware filter+encode dispatch.** The
  `kept_in_order` ArrayList becomes a list of (top-level-name,
  chunk-indices). For each kept top-level column, call
  `applySelection` on each of its chunk leaves, encode each leaf
  separately into the output, but emit a single shared schema
  subtree.

- **B1.w: rep-aware filter eval.** Today rejects nested columns
  outright. Eventually: support list-element predicates
  (`array_contains`) and nested struct field access. Squarely
  Phase E surface; B1 just needs the rejection to be clean and
  the data flow to support it later.

The encoder rep-path code (filterColumnNested + rep-level prefix
in encodeColumn) shipped in this session is *correct in isolation*
and *will be reused* once B1.x/y/z land. We don't roll it back —
it's pre-positioned for the real fix. We *don't* roll back the

work inside `fetchMetaTask` (after the footer fetch), not init-time
work — so it lands in `duration_ms`, where it's sub-millisecond on
our small-schema fixtures and lost in S3 fetch latency.

Relative gap held:
- ZPQ init **47× faster than Polars** (was 48×)
- ZPQ init **49× faster than DuckDB** (was 51×)
- End-to-end cold: ZPQ 1.69s, Polars 2.84s, DuckDB 4.06s — same
  tier separation.

Worth noting because it could have gone the other way. If we'd
built the tree eagerly in `main()` or cached it in a global, init
could have crept. Building lazily per-file was the right call.
The architectural fix that unlocked filter+encode through nested
schemas didn't cost us anything on the cold-start axis we care
most about.

### 22:40 — B2 shipped: DATA_PAGE_V2 → conformance 73%

Added the V2 page header (`DataPageHeaderV2`) to `schema.zig` —
field 8 in the `PageHeader` union, with all six required fields
(`num_values`, `num_nulls`, `num_rows`, `encoding`,
`definition_levels_byte_length`, `repetition_levels_byte_length`)
plus `is_compressed` defaulting to `true` per spec. Round-trips
through the existing thrift writer.

`page.zig` got the V2-aware `next()`: when `header.type ==
DATA_PAGE_V2`, slice the payload as `[rep_levels (uncompressed,
rep_byte_len)][def_levels (uncompressed, def_byte_len)][values
(optionally compressed)]`. Decompress only the values portion;
emit a single `bytes` slice that's `uncompressed_page_size` bytes
long with rep+def copied verbatim and values decompressed inline.
This keeps the column-side V2 installer simple — it slices by the
header lengths and treats each part as already-uncompressed.

`column.zig` got `installDataPageV2Decoder` next to the V1 one.
Differences:
- Level lengths come from the V2 thrift header, not from `<u32 LE>`
  prefixes inside the page bytes.
- Same hybrid_rle decoder otherwise — bit width derives from
  `levels.max_def` / `levels.max_rep` and our existing `bitWidthFor`
  helper.
- For BOOLEAN with V2: PlainBooleanDecoder needs `num_values -
  num_nulls` (only present values in the wire payload). V2 reports
  `num_nulls` directly so this is exact.

`advancePage` now routes V2 to the new installer instead of
`return error.UnsupportedPageType`.
