# Journal — 2026-05

## 2026-05-04

### 05:00 — Head-to-head benchmark vs Polars / DuckDB / boto3

Built a Python container Lambda (`benchmarks/python_baseline/`) with
`polars==1.36.1` + `duckdb==1.4.3`, deployed at the same memory tier
(5120 MB) and role as zpq-filter-s3. 5 warm invocations per cell.

```
Workload                    ZPQ        boto3      Polars      DuckDB
Copy 155 MB (no filter)    3107 ms    2981 ms    1895 ms ⚡  2850 ms
Stats-prune-all  9999       183 ms    n/a         1529 ms     117 ms ⚡
```

(Median of 5 warm runs. ZPQ ran multipart for copy and single-PUT
for prune-all per the auto-dispatch threshold.)

Output sizes are also informative:

```
Copy:        ZPQ 155.5 MB, Polars 117.8 MB, DuckDB 140.7 MB
Prune-all:   ZPQ 642 B,    Polars 2740 B,   DuckDB 603 B
```

Polars and DuckDB shrink the file because they decode + re-encode
with their own compression defaults. ZPQ's "byte copy" preserves the
input's exact encoding; that's a feature for ETL idempotency but not
useful when the user is trying to compress.

Three findings, in descending importance:

**1. Reader-side parallelism is now the obvious next win.** Polars
beats ZPQ at copy (1895 ms vs 3107 ms) despite doing strictly more
work (decode + re-encode). The likely cause: Polars uses
`object_store`'s parallel range-fetches; our `s3.Client` does
sequential single-stream range-fetches. The writer-side parallelism
we just shipped (5.3) doesn't help because the bottleneck moved
upstream. Mirroring the same `Io.Group.concurrent` pattern on the
read side should land a similar 2× speedup for all-survivors.

**2. DuckDB beats ZPQ at prune-all by ~60 ms** (117 vs 183 ms). Both
download only the footer and produce sub-1KB outputs. DuckDB's edge
is probably httpfs connection pooling — they keep one HTTP/2
connection alive across requests within the invocation, while ZPQ
opens a fresh TLS handshake per Lambda invocation. Worth measuring
the per-invocation handshake cost; if it's ~50-80 ms, that explains
the gap.

**3. Polars prune-all is unexpectedly slow** (1529 ms). With proper
predicate pushdown this should be sub-200 ms like ZPQ + DuckDB
(output IS 2740 B, proving it pruned all rows correctly). But
wallclock says polars actually downloaded + decoded the file before
realizing it could prune. Hypothesis: `sink_parquet` runs through
the streaming engine which may not honor row-group stats the same
way `collect()` does. Useful "if a user reaches for polars, this is
what they get" data point but not actionable for ZPQ.

Notable: ZPQ's prune-all (183 ms) is **8× faster than Polars**. The
specialized fast path is a real advantage when the user's workload
has stats-prunable filters. The catch is that the all-pass copy is
~60% slower than Polars, so ZPQ wins on selective queries and loses
on bulk copies — unless we land reader parallelism.

Container Lambda setup: `benchmarks/python_baseline/{Dockerfile,
handler.py}` + ECR repo `zpq-bench-python` + container Lambda
deployed via `aws lambda create-function --package-type Image`.
First-time setup but reusable — same machinery for any future Python
comparable.

### 04:00 — Phase 5.3 ships, multipart confirms bakeoff prediction

Skipped 5.2 (sequential multipart). Reasoning in conversation: the
bakeoff probe already implements the multipart protocol against real
S3 with parallelism on top, so a "sequential multipart" milestone
would be code strictly less than what we'd already validated.

`s3.uploadMultipart(io, arena, gpa, creds, url, body)` — modeled on
the bakeoff probe but landed as production. Dispatches each part on
its own thread via `Io.Group.concurrent`; each task owns its own TLS
connection for its lifetime (no pooling). Auto-computes part count:
~32 MB target up to 8 parts, with the 5 MB S3 floor.

Researched DuckDB's pattern (`extension/httpfs/s3fs.cpp:485`) and
Polars's (delegates to the `object_store` Rust crate's `BufWriter`).
Both use the same shape: defer the single-vs-multipart decision until
flush, based on whether one buffer was enough. Our fast path is
simpler since we know output size up front — explicit `if (out.len <
MULTIPART_THRESHOLD) put else uploadMultipart` in the dispatcher.

Lambda main upgraded from `std.process.Init.Minimal` to
`std.process.Init` to get `init.io` (a `Threaded` backend instance).
Threaded through `handle` and `handleS3Write` to `s3.uploadMultipart`.

Confirmed against the same 155 MB benchmark:

- 1769 MB tier, single-PUT (5.1): 1672 ms upload
- 1769 MB tier, multipart (5.3): 1218 ms upload (-27%)
- 5120 MB tier, multipart (5.3): 808-877 ms upload (-49% vs 5.1
  baseline; matches bakeoff's ~192 MB/s prediction at this tier)

Output round-trips through the reader: 524288 rows preserved across
4 row groups, byte-identical decode.

The upload phase is no longer the bottleneck at higher tiers — the
fetch phase (4-5 s for 155 MB read from S3) now dominates total
wallclock. That's the next obvious lever: parallelize the read side.
But we shipped a working product feature; benchmarking against
`aws s3 cp` is probably the right next move before more building.

### 03:00 — Phase 5.1 ships end-to-end on Lambda

`s3.put` (~50 LoC free function, no client pooling — see earlier
discussion) plus a new `handleS3Write` branch in `lambda/main.zig`
that swaps the per-row decode + aggregate work for stat-based
pruning + range-fetch survivors + `fastpath.build` + PUT.

Two real Lambda invocations against the 155 MB benchmark file:

| filter        | rg_pruned | bytes_fetched | bytes_out | total_ms |
| ------------- | --------- | ------------- | --------- | -------- |
| `int8>0`      | 0/4       | 155.5 MB      | 155.5 MB  | 5557     |
| `int8>9999`   | 4/4       | 0             | 642 B     | 437      |

Both outputs round-trip through ZPQ's reader correctly (524288 rows
preserved with `int8>0`; 0 rows + 0 row groups with `int8>9999`).

The `int8>9999` case is the headline product: stats prove no rows
match, so we download only the footer (~64 KB), build a 642-byte
output, and PUT. 437 ms cold-or-warm to "filter and copy" 155 MB.

Numbers worth tracking as a baseline:
- Single-stream PUT throughput: 155 MB / 1.67 s = ~93 MB/s. This is
  the 5.1 ceiling. 5.3's parallel multipart should ~2.5× this based
  on the bakeoff probe data (which hit 248 MB/s at 10240 MB tier).
- fastpath.build cost on Lambda: 241 ms to mutate offsets +
  serialize footer for 4 row groups. Negligible.
- The all-survivors case fetched 155.5 MB (almost the whole input).
  Future optimization: stream the input straight into the output
  PUT body without buffering the whole file in RAM. Phase 5.2
  multipart territory; not blocking 5.1.

### 02:15 — Two latent thrift round-trip bugs surfaced by fastpath

Writing `core/writer/fastpath.zig` (byte-copy + footer rewrite) exposed
two bugs in shared thrift-write infrastructure that nothing had
exercised before:

- `thrift.Writer.writeStructBegin/End` reset `last_field_id` to 0 on
  begin (correct, so the inner struct gets its own delta-encoding
  namespace) but never restored the outer's `last_field_id` on end.
  Subsequent outer fields then computed deltas from a stale value
  (the inner struct's last field id), so e.g. writing `data_page_offset`
  at field 9 after a nested `Statistics` struct produced a delta that
  the reader interpreted as field 11 (`dictionary_page_offset`). The
  result: data and dict offsets *swapped* on round-trip. Our reader
  code never tripped this because we hadn't been writing thrift bytes
  back out.

  Fix: writer now keeps a small stack of saved `last_field_id` values,
  pushed on `writeStructBegin` and popped on `writeStructEnd`. Stack
  depth 8 is plenty for Parquet metadata (max nesting we hit is ~3).
- `schema.zig` was writing `Statistics` at thrift field id 8 instead
  of 12. Per `parquet.thrift`, field 8 is `key_value_metadata`; 12 is
  `statistics`. Our reader handled 8 as skip, so stats were silently
  lost on every round-trip through `FileMetaData.write`. Combined
  with the bug above, this is the first version of the writer where
  stats actually round-trip.

Both fixes land independent of the fastpath feature — they were latent
bugs waiting for the first writer to exercise them.

### 01:30 — Phase 5.1 research turned up no comparables

Looked at how DuckDB, Polars, Hardwood, and Parx handle Parquet
output. None of them have ZPQ's "filter row groups, copy bytes,
renumber footer offsets" fast path. They all re-encode through their
own column-writer abstractions (`extension/parquet/parquet_writer.cpp`,
`crates/polars-parquet/src/parquet/write/file.rs`, etc.). That
makes sense — they're general-purpose engines that need a writer
hot path for arbitrary materialized output. We're an ETL tool that
wants `cp` semantics when the query is identity-on-row-groups.

So this phase is a place where we genuinely don't have prior art to
crib from. The algorithm is:

- Walk surviving row groups in order.
- For each, find its byte range
  `[min(dict_offset, data_offset), data_offset + total_compressed_size]`
  across columns.
- Append those bytes to the output buffer at `new_pos`.
- Update each column's `data_page_offset` and (if present)
  `dictionary_page_offset` by `new_pos - old_start`.
- Drop page index + bloom filter offsets (set to null) — those point
  to bytes outside the row-group region and we don't carry them
  forward in the fast path. Downstream readers fall back to
  row-group-level pruning. Re-add later if a benchmark wants them.
- Re-serialize the (mutated) `FileMetaData` via `thrift.Writer`.
- Output: `[PAR1][rg bytes][...][footer thrift][u32 LE footer-len][PAR1]`.

The plumbing we need is already in tree: `core/thrift.zig` has
read+write, `core/schema.zig` has `FileMetaData.write` and
`RowGroup.write`, `core/parquet/metadata.zig:open()` parses, and
`core/filter/*` produces the surviving-row-group bitmask. So the
new code is small — a single `core/writer/fastpath.zig` that ties
those together.

### 00:00 — `Io.Threaded` settles the writer substrate question

Going-in question (per `docs/writer_design.md` revised earlier this
session): writer uses `std.Io.Threaded` + `Io.Group`, or wire our
in-tree epoll loop into the S3 stack? Three options were on the table:
full `std.Io` port (delete loop), hybrid (loop for reads, threads for
the writer), or keep loop and build our own `InFlight(N)` mirroring
`Io.Group`'s shape. Design doc favored the hybrid a priori but flagged
"we'd have to test the loop to know it isn't even worse than threads."
Cheap-falsification path: build the threaded probe first, only invest
in the loop variant if threads fall short.

Built `probes/bakeoff_threaded`. Real S3 multipart upload of a 155 MB
payload as 8 × ~19 MB parts. Each task does its own DNS + handshake —
pessimistic, no pooling. Caller code for the parallel dispatch is
~10 lines (`Io.Group` + `group.concurrent` in a for loop, then
`group.await`).

Real bugs found along the way:

- `fb33d6a` — `src/io/http.zig` had no chunked-transfer support.
  S3 returns `Transfer-Encoding: chunked` on multipart-control
  responses (Create / Complete) with no `Content-Length`. Our
  drainResponse was reading until connection-close, which on S3 takes
  ~6s. Each multipart upload was paying ~12s of pure overhead. Reader
  code never tripped this because GETs always carry Content-Length.
- TLS partial-write — `src/io/tls.zig:Connection.send` treated
  `consumed == 0` as a hard failure. With ~MB-sized plaintexts,
  BoringSSL's `SSL_write` hits BIO back-pressure mid-stream and
  returns 0 + `WANT_WRITE` ("drain encrypted bytes, then I can take
  more"). On dev box this rarely triggered because residential
  bandwidth was so slow the BIO never filled; on Lambda's faster pipe
  it bit immediately. Fix: tolerate `consumed == 0` if encrypted bytes
  were drained. Also enabled `SSL_MODE_ENABLE_PARTIAL_WRITE` in
  `vendor/boring_tls` so SSL_write returns positive byte counts as it
  makes progress through the buffer.
- `Io.Group.async` vs `.concurrent` — `async` runs synchronously when
  the worker pool is saturated (default `cpu_count - 1`). We thought
  we had 8 parallel uploads on Lambda but were getting 1 worker
  thread + 7 deferred. Switched to `.concurrent` which guarantees
  parallelism (or `error.ConcurrencyUnavailable`).

Lambda data, warm runs, 4 invocations per tier, fresh keys:

| Memory   | par best/worst | MB/s best/worst | % of 5 Gbps |
| -------- | -------------- | --------------- | ----------- |
| 256 MB   | OOM            | —               | —           |
| 512 MB   | ~5.4s          | ~28             | ~5%         |
| 1769 MB  | 0.97 / 1.39s   | 160 / 111       | 18-26%      |
| 3008 MB  | 0.77 / 1.56s   | 201 / 99        | 16-32%      |
| 10240 MB | 0.62 / 2.85s   | 248 / 54        | 9-40% var   |

Throughput scales with memory tier — that's CPU saturation, not
network. Lambda meters CPU by memory tier, more memory = more vCPUs =
more parallel TLS encryption. No tier hits even half of 5 Gbps. At
10240 MB we crest at ~40% of theoretical. Variance at higher tiers
(10240 MB best/worst 0.62 / 2.85s) is real but probably S3 burst
throttling on rapid-fire fresh keys or cross-AZ jitter — not a
substrate property. Not investigating further now.

Despite not network-saturating, `Io.Threaded` is the right call.
An event loop is single-threaded by construction; it cannot
parallelize CPU-bound encryption across cores. At every tier with
>1 effective vCPU, threads win. The only tier where this might be
different is 256 MB, and we OOM there anyway. So no `bakeoff_epoll` —
the result is predictable from first principles.

The more interesting question that's now open: how do we get from
~250 MB/s to 500+ MB/s at the high tiers? Levers worth checking
post-5.1:

- Confirm BoringSSL is using AES-NI / ARM crypto extensions on
  Lambda's Graviton2. If not, that's the biggest available win.
- Reuse TLS sessions across the 8 parts (tickets / resumption).
  Eliminates 7× handshake cost. Probably small impact since
  handshake is ~50ms and parts take 1-3s, but cheap to verify.
- Tune `Io.Threaded.async_limit` higher than `cpu_count - 1`.
  One-line experiment.

None block the writer phase. Decision: adopt `std.Io.Threaded` +
`Io.Group.concurrent` as the writer concurrency primitive. Hybrid
model — in-tree loop stays for reader-side I/O (shipped, fine);
threads for writer parallelism. `docs/writer_design.md` updated to
reflect "decided" rather than "recommended pending data."
