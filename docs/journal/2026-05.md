# Journal — 2026-05

## 2026-05-04

### 00:00 — `Io.Threaded` settles the writer substrate question

Going-in question (per `docs/writer_design.md` revised earlier this
session): writer uses `std.Io.Threaded` + `Io.Group`, or wire our
in-tree epoll loop into the S3 stack? Three options were on the table:
full `std.Io` port (delete loop), hybrid (loop for reads, threads for
the writer), or keep loop and build our own `InFlight(N)` mirroring
`Io.Group`'s shape. Design doc favored the hybrid a priori but flagged
"we'd have to test the loop to know it isn't even worse than threads."
Cheap-falsification path: build the threaded probe first, only invest
in the loop variant if threads fall short.

Built `probes/bakeoff_threaded`. Real S3 multipart upload of a 155 MB
payload as 8 × ~19 MB parts. Each task does its own DNS + handshake —
pessimistic, no pooling. Caller code for the parallel dispatch is
~10 lines (`Io.Group` + `group.concurrent` in a for loop, then
`group.await`).

Real bugs found along the way:

- `fb33d6a` — `src/io/http.zig` had no chunked-transfer support.
  S3 returns `Transfer-Encoding: chunked` on multipart-control
  responses (Create / Complete) with no `Content-Length`. Our
  drainResponse was reading until connection-close, which on S3 takes
  ~6s. Each multipart upload was paying ~12s of pure overhead. Reader
  code never tripped this because GETs always carry Content-Length.
- TLS partial-write — `src/io/tls.zig:Connection.send` treated
  `consumed == 0` as a hard failure. With ~MB-sized plaintexts,
  BoringSSL's `SSL_write` hits BIO back-pressure mid-stream and
  returns 0 + `WANT_WRITE` ("drain encrypted bytes, then I can take
  more"). On dev box this rarely triggered because residential
  bandwidth was so slow the BIO never filled; on Lambda's faster pipe
  it bit immediately. Fix: tolerate `consumed == 0` if encrypted bytes
  were drained. Also enabled `SSL_MODE_ENABLE_PARTIAL_WRITE` in
  `vendor/boring_tls` so SSL_write returns positive byte counts as it
  makes progress through the buffer.
- `Io.Group.async` vs `.concurrent` — `async` runs synchronously when
  the worker pool is saturated (default `cpu_count - 1`). We thought
  we had 8 parallel uploads on Lambda but were getting 1 worker
  thread + 7 deferred. Switched to `.concurrent` which guarantees
  parallelism (or `error.ConcurrencyUnavailable`).

Lambda data, warm runs, 4 invocations per tier, fresh keys:

| Memory   | par best/worst | MB/s best/worst | % of 5 Gbps |
| -------- | -------------- | --------------- | ----------- |
| 256 MB   | OOM            | —               | —           |
| 512 MB   | ~5.4s          | ~28             | ~5%         |
| 1769 MB  | 0.97 / 1.39s   | 160 / 111       | 18-26%      |
| 3008 MB  | 0.77 / 1.56s   | 201 / 99        | 16-32%      |
| 10240 MB | 0.62 / 2.85s   | 248 / 54        | 9-40% var   |

Throughput scales with memory tier — that's CPU saturation, not
network. Lambda meters CPU by memory tier, more memory = more vCPUs =
more parallel TLS encryption. No tier hits even half of 5 Gbps. At
10240 MB we crest at ~40% of theoretical. Variance at higher tiers
(10240 MB best/worst 0.62 / 2.85s) is real but probably S3 burst
throttling on rapid-fire fresh keys or cross-AZ jitter — not a
substrate property. Not investigating further now.

Despite not network-saturating, `Io.Threaded` is the right call.
An event loop is single-threaded by construction; it cannot
parallelize CPU-bound encryption across cores. At every tier with
>1 effective vCPU, threads win. The only tier where this might be
different is 256 MB, and we OOM there anyway. So no `bakeoff_epoll` —
the result is predictable from first principles.

The more interesting question that's now open: how do we get from
~250 MB/s to 500+ MB/s at the high tiers? Levers worth checking
post-5.1:

- Confirm BoringSSL is using AES-NI / ARM crypto extensions on
  Lambda's Graviton2. If not, that's the biggest available win.
- Reuse TLS sessions across the 8 parts (tickets / resumption).
  Eliminates 7× handshake cost. Probably small impact since
  handshake is ~50ms and parts take 1-3s, but cheap to verify.
- Tune `Io.Threaded.async_limit` higher than `cpu_count - 1`.
  One-line experiment.

None block the writer phase. Decision: adopt `std.Io.Threaded` +
`Io.Group.concurrent` as the writer concurrency primitive. Hybrid
model — in-tree loop stays for reader-side I/O (shipped, fine);
threads for writer parallelism. `docs/writer_design.md` updated to
reflect "decided" rather than "recommended pending data."
