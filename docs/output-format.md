# Output format

This page is the contract for what `zpq query` prints on stdout, and for the JSON value of each type. The CLI, the
Lambda's `agg` response and libzpq share one writer for aggregate values, so those print the same way.

## Framing

The answer is the only thing on stdout. Diagnostics, and the summary that `--summary=json` asks for, go to stderr.

| `--format` | Shape | No rows |
|---|---|---|
| `ndjson` (default; `jsonl` is an alias) | one JSON object per row, each followed by `\n` | nothing (0 bytes) |
| `json` | one array of row objects on one line, then `\n`: `[{...},{...}]` | `[]` |
| `csv` | RFC 4180: a header row, then one record per row | the header row only |
| `parquet` | a Parquet file (needs `-o FILE`, `-o -`, or a stdout that is not a terminal) | a file with no rows |

The JSON output has no whitespace between tokens. Each row object has one key per output column, in column order:
- for `--columns`, the order of the file's schema;
- for `--select` and SQL, the order of the list;
- for an aggregate, the GROUP BY keys and then the aggregates, in the order given, or in SQL's SELECT order.

A key is the column's name or its alias. A STRUCT leaf is named by its dotted path (`"st.a"`). Repeated columns (LIST,
MAP) are refused in row output.

A query that fails part-way can leave a partial answer on stdout, and exits non-zero. Check the exit status
(`set -o pipefail` in a pipeline).

## Validation and skipped data

zpq validates every byte that can affect the answer; corruption confined to data proven irrelevant
(unprojected columns, columns a COUNT pass does not read, items an exact admit/sketch bound excludes)
may go undetected. This is a query contract, not a whole-file integrity check, and is subject to the
existing statistics trust boundary below.

Filtered scans decode a payload column (one the filter and the group keys do not read) after the filter, and
pass by its header any data page of an optional flat payload column with no surviving row:
a payload page whose rows the filter rejects is not decoded, so its corruption is not reported.
Which pages those are depends only on the input and the query (the decoded, validated filter columns and the
payload page headers, which are read and checked like any other), never on worker count, memory budget,
decode path or hardware sizing. Every payload page that is decoded follows the canonical error order below.

Sketch/census counts, fingerprints, first-appearance prefixes and admit certificates use keys and predicates
that have actually been decoded and passed normal decoder validation. Skipped aggregate arguments do not
supply these proofs. Collisions only widen admission; an uncertified bound falls back to the exact scan.
Footer sizes and NDV estimates may choose a plan or size storage; they do not certify a sketch/census exclusion.
Sketch, census and first-key multipass plans reject every gated input, including both streams and gated
local readers with a mapping. They cannot rerun a source whose bytes have been returned to its producer.

Separately, zpq prunes on footer/page statistics that pass corroboration: compatible type/order, counts,
bounds and consistency checks, plus the [known writer-version policy](writer-statistics.md). Corroboration does not compare those claims with all decoded values.
Internally consistent but false statistics can therefore produce a different answer from a full scan.
`--trust-stats` accepts additional plausible claims and statistics-as-answer; `--scan-all` ignores statistics.
It still projects columns and may use exact decoded sketch/census proofs, so it is not whole-file validation.

The fixture `ci/fixtures/parquet/false_bounds.parquet` pins this boundary. Its decoded rows have
`x = [100000,100001,100002]` and `v = [10,20,30]`, while the footer claims `x` is between 200000 and 200002.
`SELECT sum(v) AS s ... WHERE x=100001` currently returns NULL by default and 20 under `--scan-all`.
The fixture is generated by `write_false_bounds()` in `tools/gen_stats_order_fixtures.py`; the core test checks
both results deliberately. Canonical ordering after an observed decode failure is described in
[decode-errors.md](decode-errors.md).

## Row output

Without `--aggregate`, `--group-by` or a SQL aggregate, zpq prints one object per matching row:

```
$ zpq query tiny.parquet --filter 'value > 10'
{"id":2,"group":"a","value":20}
{"id":3,"group":"b","value":30}
```

## Aggregates without GROUP BY

A scalar aggregate prints exactly one row, even over no input rows. There, `count` is `0` and every other aggregate is
`null`:

```
$ zpq query tiny.parquet --aggregate 'count(*) AS n, sum(value) AS s, avg(value) AS a'
{"n":3,"s":60,"a":20}
$ zpq query tiny.parquet --filter 'value > 100' --aggregate 'count(*) AS n, sum(value) AS s, avg(value) AS a'
{"n":0,"s":null,"a":null}
```

`--format json` wraps that row in an array: `[{"n":3,"s":60,"a":20}]`.

## GROUP BY

GROUP BY prints one row per group: the keys first, then the aggregates. A NULL key is a group of its own, with a
`null` key. Groups come in the order they first appear in the input (files as given, then row groups, then rows), at
every `-j`. `--unordered` gives up that order, and `ORDER BY` in SQL sets one. A GROUP BY that matches no rows prints
no rows: nothing in NDJSON, and `[]` in JSON.

```
$ zpq query tiny.parquet --group-by group --aggregate 'count(*) AS n, avg(value) AS mean'
{"group":"a","n":2,"mean":15}
{"group":"b","n":1,"mean":30}
```

## Values

A value prints the same way wherever it appears: in a row, as a GROUP BY key, or as a `min`/`max`. SQL NULL is `null`.

| Type | JSON | Example |
|---|---|---|
| INT8 to INT64 | integer | `-2`, `9223372036854775807` |
| UINT8 to UINT64 | integer, unsigned | `18446744073709551615` |
| integer `sum` | integer, exact. It can be past 64 bits, so parse JSON integers as arbitrary precision | `27670116110564327421` |
| DOUBLE, FLOAT, FLOAT16 | number, the shortest decimal that reads back as the same value, never with an exponent | `1.5`, `0.1`, `-0` |
| a float that is NaN or infinite | string | `"NaN"`, `"Infinity"`, `"-Infinity"` |
| DECIMAL(p, s) | number, exact, with all `s` fractional digits | `1.50`, `-0.05`, `300.00` |
| BOOLEAN | `true` / `false` | `true` |
| STRING, ENUM, JSON | string | `"a\"b"` |
| DATE | integer: days since 1970-01-01 | `19724` (2024-01-02) |
| TIME | integer, in the column's unit (ms, µs or ns) since midnight | `43200250` (12:00:00.250, ms) |
| TIMESTAMP | integer, in the column's unit (ms, µs or ns) since 1970-01-01 00:00 | `1704164645600000` (µs) |
| INT96 timestamp | integer: nanoseconds since 1970-01-01 00:00 | `1704070800000000000` |
| bytes, UUID, INTERVAL, BSON, GEOMETRY | see [binary-output.md](binary-output.md) | `{"base64":"/wA="}` |

Notes:
- **Floats.** A double that holds a whole number prints without a fraction (`1`, `15`), so a reader may take it as an
  integer: read numbers by value, not by their spelling. Large and tiny doubles print every digit: `1e300` prints as
  `1` followed by 300 zeros. The NaN and infinity strings are needed because JSON has no literal for them. In CSV they
  are the bare words `NaN`, `Infinity` and `-Infinity`.
- **Decimals.** A DECIMAL is written as exact text. A reader that parses JSON numbers as decimals (Python's
  `json.loads(s, parse_float=decimal.Decimal)`) gets the value exactly. One that parses them as doubles gets the
  nearest double.
- **Dates and times.** In JSON, DATE, TIME and TIMESTAMP print as their stored integers, and do not say their unit.
  Read the unit from `zpq schema`. CSV prints them as ISO text with the column's own fractional digits, and adds `Z`
  when the column is adjusted to UTC: `2024-01-02`, `12:00:00.250`, `2024-01-02 03:04:05.600000Z`.
- **Strings.** JSON escapes `"`, `\`, `\n`, `\r`, `\t` and the other control characters (`\u0001`), and also
  U+2028 and U+2029. All other text passes through as UTF-8. A STRING value that is not valid UTF-8 is an error (exit
  1), not a replacement character.
- **CSV.** NULL is an empty unquoted field and the empty string is `""`. Bytes follow
  [binary-output.md](binary-output.md).

## Aggregate values

| Aggregate | JSON | Parquet (`-o`) |
|---|---|---|
| `count(*)`, `count(x)`, `count(DISTINCT x)` | integer, never null | INT64, required |
| `sum(x)`, integer `x` | integer, exact (see above); `null` over no values | INT64. A sum past 64 bits is refused (`AggIntTooWide`) |
| `sum(x)`, float `x` | number, or a NaN/infinity string | DOUBLE |
| `sum(x)`, DECIMAL(p, s) `x` | number with `s` fractional digits | DECIMAL(38, s) |
| `min(x)`, `max(x)` | as `x` prints | the type of `x` |
| `avg(x)`, integer or float `x` | number (DOUBLE); `null` over no values | DOUBLE |
| `avg(x)`, DECIMAL(p, s) `x` | number with `s + q - p` fractional digits, where `q = min(38, p + 4)` | DECIMAL(q, s + q - p) |
| `avg_state(x)` | `{"sum":..,"count":..}` | two columns, `<name>__sum` and `<name>__count` |

`avg(x)` is the mean as one plain number, in every format. For integer `x`, the integers are summed exactly and the
sum is divided by the count once. For DECIMAL(p, s), the mean is exact and rounded half away from zero. It has up to
four more fractional digits than `x`, and never fewer integer digits: DECIMAL(9, 2) gives DECIMAL(13, 6), and p = 38
keeps the input type.

`avg_state(x)` is the same average, kept as state that you can merge. Its `sum` is a DOUBLE for integer and float `x`,
and DECIMAL(38, s) for DECIMAL `x`. Its `count` is the number of non-null values. Over no values it is
`{"sum":null,"count":0}`. To get the overall mean across files or Lambda invocations, divide the sum of the `sum`s by
the sum of the `count`s. Averaging per-file means gives the wrong answer. In CSV, `avg_state` is the two columns
`<name>__sum` and `<name>__count`.

```
$ zpq query tiny.parquet --group-by group --aggregate 'avg_state(value) AS st'
{"group":"a","st":{"sum":30,"count":2}}
{"group":"b","st":{"sum":30,"count":1}}
$ zpq query tiny.parquet --group-by group --aggregate 'avg_state(value) AS st' --format csv
group,st__sum,st__count
a,30,2
b,30,1
```

## The --summary=json line

`--summary=json` adds one JSON line on stderr once the answer is flushed and any named output file is published.
Without it nothing is printed there on success. A failure prints `{"type":"error","ok":false,"code":..,"message":..}`
instead, where `code` is the error's name and `message` the sentence the CLI would print.

```
$ zpq query tiny.parquet --filter 'value > 10' --aggregate 'count(*) AS n' --summary=json
{"type":"summary","ok":true,"rows":1,"output":null,"rows_in":3,"rows_scanned":3,"rows_matched":2,"bytes_in":1664,
"bytes_out":8,"files_in":1,"row_groups_in":2,"row_groups_pruned":0,"row_groups_full_match":1,"cols_stat_pruned":0,
"codec":null,"membership":{...},"total_ms":0,"total_us":461,"output_us":14,"wall_ms":{"open":0,"parse":0,"scan":0,
"footer":0},"worker_ms":{"decode":0,"filter":0,"fold":0,"encode":0,"sink":0}}
```

(one line; wrapped here.)

### Rows

| Field | Counts |
|---|---|
| `rows` | rows in the answer, printed or written; after GROUP BY, HAVING, ORDER BY and LIMIT (1 for a scalar aggregate) |
| `rows_in` | every row of every input file |
| `rows_scanned` | rows in the row groups read: `rows_in` less what statistics or Bloom filters ruled out, and, under a LIMIT, never reached |
| `rows_matched` | rows of `rows_scanned` the filter kept (all, without one): what an aggregate folds, a write writes, and row output prints before ORDER BY and LIMIT |

`rows_matched <= rows_scanned <= rows_in` always holds. A row output under a LIMIT stops reading once the limit is met,
so its `rows_scanned` and `rows_matched` count only what was read. The counts are the same at every `-j`, except for
a LIMIT top-N, whose workers may each read a row group before a cut passes over the rest.

### Time

Every field is whole milliseconds (`_ms`, rounded down) or microseconds (`_us`).

- `total_ms` / `total_us`: wall-clock time of the query, from parsing the command to the summary.
- `output_us`: wall-clock time from the first output encoding or write through flushing and publication of the
  answer. Includes waits between output writes while scanning continues; never exceeds `total_us`. Worker encode
  and sink times remain in `worker_ms` and may exceed wall-clock time when summed across workers.
- `wall_ms`: wall-clock phases.
  - `open` opens the inputs and reads their footers.
  - `parse` parses the footers and the query.
  - `scan` covers reading the row groups (decode, filter, aggregate or encode), from the first to the last.
  - `footer` writes the output file's Bloom filters and footer (for an aggregate, its whole answer file).

  The phases run one after another, except that S3 data reads continue during `scan`. Their sum is at most
  `total_ms`; the rest is planning, the merge of the workers' results, and printing.
- `worker_ms`: each worker's time in each step of the scan, **summed over all workers**.
  - `decode` decompresses and decodes pages.
  - `filter` evaluates the filter.
  - `fold` folds rows into the aggregates (aggregates only).
  - `encode` encodes Parquet output (writes only).
  - `sink` writes the encoded bytes.

  One worker's steps do not overlap one another, but the workers run at once. With N workers, a step's sum can reach
  N times `wall_ms.scan`, and the steps' total divided by `wall_ms.scan` is roughly the parallelism the scan achieved.
  A large `worker_ms.decode` beside a small `wall_ms.scan` is many workers decoding at once, not a slow decode.

The Lambda's and libzpq's responses use the same row counters and the same `wall_ms` / `worker_ms` objects; a write's
`wall_ms` adds `mp_await` and `mp_complete` for its multipart S3 upload.
